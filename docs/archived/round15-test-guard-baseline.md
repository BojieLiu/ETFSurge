# round15 测试防护基线（test-guard-baseline）

> **定位**：把 round14 诊断（docs/round14-container-acceptance-diagnosis.md §4 测试盲区）暴露的防护体系缺陷，升级为一套**可落地、可进 pre-commit 的防护基线规范**。round14 是"发现问题"，本文件是"规定测试怎么写才对"。
>
> **性质**：基线规范 + 首批落地用例清单。**不实施**（落地见 §6 优先级，按「先规范后铺量」推进）。
>
> **一句话**：现有防护证明"代码能编译、能跑、契约一致"，但几乎不证明"数据对、行为对、不慢、不假完成"。本基线把断言语义从**非空/200/枚举**上提到**内容正确与行为正确**。

---

## 0. 问题回顾（为什么 20+ 项问题全逃逸——5 类盲区）

round14 §1 结论速览 25 项（除 2 项通过/提示外 20+ 项问题，含 §4 盲区表 8 行）无一被既有防护拦住。归类成 5 类盲区模式（每类是可辨识的测试设计缺陷，而非"漏写用例"）：

| # | 盲区模式 | 表征 | 逃逸问题 |
|---|---|---|---|
| ① | **只验格式/枚举集合，不验行为** | 断言"返回 200/非空/在枚举内"，不验"真实值对不对" | 因子伪 IC、sentiment 恒 fallback、资讯未收录 |
| ② | **mock 理想输入喂养** | `patch` 掉真实函数 + `MagicMock` DB，喂格式完美的假数据 | apply-design 断裂、公众号空串、watchlist 慢（mock 掉慢源） |
| ③ | **前后端契约盲区** | 契约文件勾选 ✅，但 `check_routes` 只扫路由存在性，不验响应结构 | 设置页 2 处联调错位、因子页中文名前端未消费 |
| ④ | **CSS/视觉零覆盖** | vitest jsdom `css:false` 不层叠样式 | 盈亏色失效、方案卡布局挤、下拉不关（行为级交互无用例） |
| ⑤ | **性能/降级无门禁** | 无耗时断言、无降级触发条件断言 | 冷缓存慢、江波龙路径、港股自选超时、LLM 超时（降级被固化） |

**共同根因（一句话）**：防护体系把"能编译、能跑、契约一致"当成了"功能正确"。测试数据源被理想化、断言停留在非空层、视觉与前后端联调没有机器可验证的断言。

## 1. 防护基线总则（所有新增测试的必守规定）

**R1. 断言语义最低为"内容正确"而非"非空/200"**
- 反例：`assert response.status == 200`、`assert len(rows) > 0`。
- 正例：断言**关键字段的真实值**（如 `ic_sample_count >= 30` 才判有效、行情 `price` 非 fallback 默认值、报告 news 首条不是 A 股雷同）。
- 例外：纯"路由可达/权限"烟测可用非空，但**必须打标**为 smoke 而非行为断言。

**R2. 每个降级/兜底路径都要有一句"它何时不该被当成成功"的负向断言**
- 降级路径可能仍返回非空且 200——这既是功能也可能掩盖故障。
- 凡有 fallback 的函数，测试必须断言：**数据源存活时输出带真实来源标记；源全挂时输出带 `source/reason` 或 `_degraded` 降级标记，且不得冒充满血结果**。
- 具体先例：`_last_ic_batch` 空时 IC 值应为 None（round14 P0-C 断言）、watchlist 降级注入 `_degraded`（P0-D）。

**R3. 新增用例必须有可能失败（先写 FAIL，再实现）**
- 全恒绿（只 assert 存在/非空/200）的新用例视为未完成，review 拦截。
- 落地手法：写用例 → 跑出 FAIL → 实现 → 转绿。P2-AD 下拉不关是现成范本（临时测试 `doAnalyze 后 showDropdown 仍 true` FAIL 实证）。

**R4. 前后端联调必须有真实 payload 的联合验证**
- 契约文件勾选 ✅ 不算数；`check_routes` 扫到路由存在不算数。
- 至少为每个关键 POST 端点留一条**前端真实消费形态**的用例（前端透传的字段结构 → 后端处理），而非只测后端理想的 `symbols+weights` 形态。

**R5. 视觉/交互行为必须有组件级行为用例**
- 不只测"元素存在"，测"状态流转"：点按钮 → 下拉关/SSE 结束 → 结果渲染 → 错误/空态分支。
- CSS 特异性/优先级覆盖这类回归，jsdom 测不到时，用**读编译后样式或源码 style 块**的源码级断言兜底（先例：P1-K 的 `fs.readFileSync` 断言 `text-up/down` 覆盖规则存在）。

## 2. 五模式对应的具体基线（A–E）

### 基线 A：残缺/降级路径负向测试（治盲区②⑤）
- **对象**：所有 fetch_* / 多源降级链 / get_* 兜底分支。
- **规范**：每个降级链测试至少覆盖三态：`源1可用 → 主源结果`、`源1挂源2可用 → 降级`、`全挂 → 降级标记（不冒充满血）`。
- **断言语义**：输出必须可区分"真数据 vs fallback"。无来源标记的降级输出 = 缺陷。
- **首个用例**：
  - `fetch_history('AAPL','US')` 三层降级链——mock akshare 挂 → 断言走 Finnhub/AlphaVantage 且返回 ≥N 行（当前仅宿主机实测 100 行，单测无）；mock 全挂 → 断言返回空且日志标 `fallback chain`。
  - **LLM 策略检查（round14 P0-B 测试 1+2）**：mock provider 慢响应 → 断言兜底在 `_llm_timeout_for` 预算内完成而非 CancelledError 穿透，且 `(max_retries+1) × providers × request_timeout ≤ 0.9×预算`（当前完整档 2×2×35=140 > 81 应 FAIL——防"重试轮次总耗时超外层预算"回归）。
  - 因子 IC：样本 <30（或约定阈值）→ `ic_val=None` + 状态"未累积"，**不产生"反向已下架"误导**（round14 P0-C）。

### 基线 B：内容正确性断言（治盲区①）
- **对象**：factor、sentiment、regime、news 分级、report 等"判断/汇总"型输出。
- **规范**：可量化指标断言真实值落在合理区间，且**当数据源存活时才用到标称值，否则显式降级标注**。
- **首个用例**：
  - sentiment：mock 存活 → 返回 `[20,80]` 内 + `source` 不降级；mock 全挂 → 返回 + `_degraded: true`（当前 `test_pipeline_sentiment_injection.py` 只验 `sentiment_history` 结构存在 + `sentiment_index` 为数值类型，源全挂的降级默认值 50 也在合法区间内恒绿通过）。
  - news 分级：某**未收录关键词** → 断言落到某默认级且**不被误标为高 importance**；新增一例"未知新闻不得拿 highest stars"（当前只测已知词典内）。

### 基线 C：组件行为用例（治盲区④）
- **对象**：所有带交互的组件（搜索下拉、分析按钮、SSE 进度、tab 切换、自选增删、板块分析入口）。
- **规范**：每个交互组件至少一条"多步行为链"用例：`用户操作 → 状态流转 → 终态`，含 loading/空/错误/慢 四态。
- **首个用例（P2-AD 下拉不关）**：
  - 输入关键词 → 下拉显示 → 点「分析」→ 断言 `showDropdown === false`（当前 FAIL 已实证）+ `doAnalyze` 被调。
  - 现有 22 用例补一条负向路径：搜索无结果 → 下拉显示空态（不转圈不崩溃）。

### 基线 D：前后端联调真实 payload 联合验证（治盲区③）
- **对象**：apply-design、设置保存、search 各 kind、analysis stream、watchlist add/remove。
- **规范**：每条关键 POST 留一条"真实前端形态"用例；`check_routes`（可选增强）从扫路由升级为实例化 Pydantic 响应模型校验。
- **首个用例（apply-design）**：
  - 用 `DashboardAiTools.vue applyPlan()` 真实构造的 payload（当前 `patch` 掉真实 `apply_portfolio_design` + `MagicMock` DB）→ 去 mock、真实函数 → 断言 `applied` 与前端传入 symbols 一致；空 symbols → 400（round14 P0-A 后端加固约定）。

### 基线 E：性能软门禁自动化（治盲区⑤，软门禁不阻断）
- **对象**：watchlist、搜索、factor-health、symbol-analysis、综合研判（热点路径）。
- **规范**：`verify_perf.py` 对热点路径设耗时上界（沿用 AGENTS.md 阈值：watchlist ≤3s、搜索 ≤1s、factor-health ≤2s），超时**预警登记**不阻断提交（保持软门禁性质）。
- **首个用例**：冷缓存首请求 watchlist 耗时（round14 冷缓存性能盲区）——记录基线值供后续排期。

## 3. 与现有 pre-commit 13 段的差异化定位

依据 AGENTS.md「新增门禁须说明差异化价值」（2026-08-09 治理约定），本基线的五条**不新增静态检查段**，而是**约束 pytest 用例的产出形态 + 补一条性能软门禁**：

| 现有检查 | 验证什么 | 本基线补什么 |
|---|---|---|
| pytest（-n auto） | 跑绿，量：新增用例数 | **质**：断言语义内容正确（R1/R2/R3） |
| check_routes | 路由存在性/契约文件一致 | **响应结构运行时校验**（基线 D 可选增强） |
| smoke_startup | 服务能起 | **真实数据源内容**（R2 降级标记） |
| mypy / audit_async_blocking / build | 类型 / 阻塞 / 编译 | 视觉与行为（基线 C，jsdom 层） |
| —— 无 —— | —— | **性能软门禁**（基线 E，verify_perf.py） |

**治理约束**：基线 A–E 是**规范 + 用案例**，不新增 shell 门禁段（死代码防膨胀约定）。唯一可能新增的是基线 E 的 `verify_perf.py`，且为**软门禁**（预警不阻断，符合 AGENTS.md 性能验收口径）。

## 4. 断言语义速查表（新增测试对照使用）

| 断言目标 | 应断言 | 不应只断言 |
|---|---|---|
| fetch 降级链 | 主源/降级/全挂 三态 + 来源标记 | `len > 0` |
| 因子 IC | `sample_count >= 阈值` 才有效 | `ic in [-1,1]` |
| sentiment/regime | 存活时标称值 + `_degraded` 区分 | `返回 0-100 区间` |
| news 分级 | 未收录词落在合理级 + 不打高星 | `返回 list` |
| 前端交互 | 行为链终态（下拉关/状态流转） | `元素存在` |
| 颜色/布局 | 读样式/源码风格覆盖规则 | `class 存在`（css:false 测不到覆盖） |
| POST 联调 | 真实 payload → 响应字段一致 | `200` / `len > 0` |
| 性能 | 耗时 ≤ 阈值（软门禁） | 无 |

## 5. 落地优先级（建议顺序）

1. **基线 C+P2-AD 首个用例**（最高杠杆）：先写 FAIL 单测再实现，立即可验证防 X 效果；与 round14 P2-AD（下拉不关修复）天然合并。
2. **基线 A 降级链**：fetch_history(US) 三层 + 因子 IC 样本保护，覆盖 round14 P0-C。
3. **基线 D apply-design 真实 payload**：去 mock + 契约 payload，覆盖 round14 P0-A。
4. **基线 B sentiment/news 内容断言**：补降级标记 + 未知词分级。
5. **基线 E verify_perf.py**：登记冷缓存基线，排期优化。

> **反假完成自检**：每落一条新基线，必须能举出一个"该基线防住的具体问题"（如 C→P2-AD、A→P0-C/P2-AN、D→P0-A）。若一条基线举不出它防住的真实问题，说明是冗余规范，应删。
