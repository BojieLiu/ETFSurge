# 容器全链路诊断 —— 完整提示词模板

> **触发词**：`容器全链路诊断`（见 AGENTS.md 指针）。你说触发词 + round 文档路径（可选），
> 即读取本模板并严格按它执行。不提供 round 文档路径时默认取 `docs/` 下最新 round*.md。
>
> **模板会过时**：基线数字（耗时/填充率）随轮次更新，执行时以触发轮次的 round 文档实测基数为准，
> 本模板只保留流程骨架与已知基线参考值。

---

# 目标
对 ETF Surge 做一次「构建镜像 → 起容器 → 全链路诊断 → 对照 round 文档验证 → 分析结果质量审查 → 修复方案 + review」的完整验证轮。

**诊断产物落盘规则（强制）**：本轮诊断结论**写入一篇全新的 round 文档**（`docs/roundN+1-xxx.md`，N = 被诊断文档的轮次），
**绝不追加/改写被诊断的旧 round 文档**——旧文档只读，作为对照基准；新发现按 R 系列编号写入新文档，
新文档承载「本轮实测 + 对照验证矩阵 + 新问题 R 系列 + 修复方案 + review」，与被诊断轮次清晰分离（round31 实践：round30 只含 R85-R92，R93-R98 独立成 round31）。

# 阶段与边界（强制）
按五个阶段推进，每阶段结束汇报，等待指令后才进入下一阶段：
1. 环境构建与启动
2. 全链路诊断 + 对照 round 文档验证（只诊断、不写代码）
3. 分析结果质量审查（组合设计 / 策略检查 / 各分析报告）
4. 问题分析与修复方案 + **测试防护体系缺口分析**（只写方案文档，不写修复代码）
5. 方案 review（三轮结构化）

未收到明确指令，不得进入实施/写修复代码/commit/push。

# 环境步骤
1. 停止上一轮遗留容器（若在运行）：`docker-compose down`（防旧容器占端口/资源）
2. 构建并启动生产态镜像：`docker-compose up --build --profile prod`（迭代验证可用 dev profile）
3. 记录：镜像构建耗时、容器启动耗时、后端就绪时间（warmup 需 60s+，看 backend.log）
4. 确认前后端存活：`docker-compose ps` + 浏览器访问 http://localhost
5. **回收老版本镜像**：`docker image prune -f`（构建完成后上一轮镜像层变 dangling，清掉；只清 dangling，不动其他项目镜像）
6. 全程只起这一次容器，所有诊断在这一实例内完成，不反复重启

# 资源回收（诊断分析完成后，收尾）
在阶段 4 完成后、且确认本轮无需再进容器复测时执行；最迟在最终汇报前：
1. **停止并移除当前容器**：`docker-compose down`
2. 核对：`docker ps` 应无本项目容器
3. 回收前确认诊断证据已留存（日志 / 接口响应 / DB 快照），防证据随容器消失
注意：若 review 阶段发现需在容器内复测的 FAIL 项，先复测再回收

# 文档归档（round 定稿后，收尾）
在阶段 5（Review 三轮）完成、round 文档最终定稿后、最终汇报前执行（对照 `docs/archived/README.md` 归档原则）：

1. **识别适合归档的文档**：
   - 已完结轮次的 `round*.md`：该轮全部待验证项 / 修复项已关闭（验证矩阵无 FAIL 遗留）、
     无活跃实施依据身份（已全部落地或被当前轮文档承接）
   - 已被当前轮文档取代的旧轮文档（本轮 roundN 定稿后，roundN-1 及更早若再无活跃引用即可归档）
   - 一次性诊断 / 评审产物：方案评审、diag 日志（`logs/diag/*`、`diag/out/*`）、单标的诊断输出
2. **不归档**：当前轮 round 文档、`docs/design-checklist.md`（常驻设计清单）、
   `docs/patrol-orchestration-plan.md`（常驻流程）、`docs/prompt-templates/`（常驻模板）、
   `api-contracts/`（活跃契约）、README / AGENTS（项目说明）
3. **执行归档**：`git mv docs/roundXX-xxx.md docs/archived/`（保留 git 历史，勿用普通 mv）
4. **同步引用**：`rg "roundXX"` 全仓排查旧路径引用（docstring / 注释 / 测试 / 前端），
   统一改指 `docs/archived/...`；有活跃语义的引用方（如 README Known Issues 指针）改指
   archived 路径或注明已归档
5. **登记**：在 `docs/archived/README.md` 顶部追加「最近一次归档」条目
   （归档清单 + 承接映射 + 引用同步清单 + 不归档说明），格式仿照既有条目
6. **校验**：`docs/` 根目录仅剩当前轮 round 文档 + 常驻文档；`rg "docs/roundXX"` 无残留死引用
   （仅剩 `docs/archived/` 内自身引用为正常）
   > 归档只动文档，无需跑巡检；commit 时 pre-commit 对纯文档提交（仅 staged docs/diag/api-contracts）
   > 自动走短路跳过编译与测试门禁（仅保留密钥扫描）；若引用同步顺带改了代码文件则短路失效、
   > 按正常逻辑变更走门禁。确认无需复测时再执行资源回收

# 前端 Lighthouse 评分（性能/可访问性，软门禁）
在「前端页面四态」之外补量化指标——对容器内生产前端（nginx :80）跑 Lighthouse 评分：

1. **URL**：`http://localhost/`（首页）+ `http://localhost/dashboard`（Dashboard）。
   容器 prod profile 前端在 :80（根目录 `.lighthouserc.js` 里的 `localhost:3000` 是本地
   preview 端口，容器诊断以 :80 为准，**不得用 dev server :5173 冒充生产评分**）。
2. **方法**：每页 2 次采样（对齐 R4-19 口径：lighthouse + headless-shell），
   取中位数或次优值；环境未装 lhci 时用
   `npx lighthouse <url> --only-categories=performance,accessibility,best-practices,seo --output=json --output-path=data/lighthouse_report.json --chrome-flags="--headless --no-sandbox"`；
   已装 lhci 则 `lhci autorun --config=.lighthouserc.js`（注意其 URL 默认指向 :3000，需按上条覆盖）。
3. **基线（F18 / `.lighthouserc.js` / 上轮实测）**：
   | 类别 | 阈值 | 性质 |
   |---|---|---|
   | Performance | ≥ 60 | 硬门禁（error 断言） |
   | CLS | < 0.1 | 硬门禁（error 断言） |
   | Accessibility | ≥ 80 | 软门禁（warn；round29 R64 实测 86→100） |
   | Best Practices / SEO | ≥ 80 | 软门禁（warn） |
   | LCP / TBT | ≤ 8s / ≤ 500ms | 参考 warn |
   - **软门禁语义**（AGENTS.md「性能验收」）：超阈值**不阻断诊断 DONE**，记入 round 文档
     「已知性能债」清单（路径 + 实测值 + 阈值）后续排期；`.lighthouserc.js` 内 error 断言
     是 lhci 跑分时的门禁，与「round 验收软门禁」两级口径并存。
4. **产物**：`data/lighthouse_report.json`（覆盖上一份）+ round 文档记录
   四类别分 + 核心 Web Vitals（LCP/CLS/TBT/SI）+ 与上轮/基线对比，逐项标 PASS/WARN/FAIL。
5. **负向**：采样 < 2 次不得作为结论；容器内抓不到页面（nginx 未起 / JS 报错）记为
   「待复测」而非评分 FAIL。

# 分析结果质量审查（四问法，逐句不整体）
对组合设计 / 策略检查 / 各分析报告的每一条结论，走四问并输出判断质量矩阵：
1. 事实 or 推断？——事实可查证（数据中能直接找到），推断需支撑
2. 推断的支撑在哪？——对应到具体因子值 / 权重 / 实测相关性 / 行情数据（file:line + 数值），
   无支撑 = 臆断（示例：round30 港股「相关性较高」实测 513120×512890 仅 +0.120）
3. 有无反例或内部矛盾？——自相矛盾 = 不可信（示例：「13/13 无兜底」vs「33.3% 覆盖」）
4. 与当下行情一致吗？——跨数据源核对；陈旧/占位数据下的判断 = 失效
   （示例：红利/恒科偏弱仅技术面信号无因子支撑，且 KDJ J 90.11 vs 6.90 冲突）

结论分级：合理 / 部分合理（缺支撑）/ 臆断（无支撑）/ 失效（陈旧或占位数据）

输出判断质量矩阵：
| 判断原文 | 事实/推断 | 数据支撑（file:line+数值） | 与当下行情一致? | 结论（合理/部分合理/臆断/失效） | 修复建议 |
矩阵后汇总：可采信结论 N 条 / 需修正 M 条 / 臆断 K 条，附一句话总体评价

数据准确性抽查（抽检关键数值）：
- 权重：portfolio_etfs.target_weight 之和 = 1 − 现金，设计结果与 DB 一致
- 价格/涨跌：报告引用值与 realtime 接口核对
- 因子：factor_availability 计数 + 占位检测（RSI 50.0 / 动量 +0.300 / ln_mcap 0.0 均为占位值）
- 报告数值：报告引用值 vs DB 源数据（如「中证A500ETF 20%」→ portfolio_etfs.weight=0.20 实测）
- 相关性：用 kline_cache 实测计算，禁止无数据断言
- 新鲜度：as_of / data_source / estimate_source 字段，确认无过期兜底

# 对照 round 文档验证（核心步骤）
1. 通读 round 文档，提取所有「待验证项 / 验证窗口项 / 未决项 / 已修复项」，以及 memory 中该轮的事实记录
   **（只读基准：被诊断的 round 文档不改写、不追加；本轮发现全部写入新建的 roundN+1 文档）**
2. 对每项生成验证矩阵：
   | round 项 | round 文档预期 | 本轮实测 | 结论 PASS/FAIL/不适用 | 证据（接口响应值/日志/DB 查询/耗时） |
3. 区分三种状态，不要混为一谈：
   - 已验证已修复 → 本轮复测确认
   - 已设计未实施（如 R85-R92）→ 标记「未实施，本轮不适用」，只诊断环境是否已自然缓解
   - 仍待验证 → 本轮补测
4. FAIL 必须附证据链（file:line + 实际值），禁止只说「现象」
5. 已修复项给出「修复前 vs 修复后」对比数据

# 诊断与方案要求
- 每个症状：机制链条（症状 → 根因，每环节 file:line）+ 数据实证（DB/缓存/日志真实记录，禁纯推断）
- 区分归因：架构缺陷 vs 环境偶发 vs 数据源外部问题
- 新发现问题按 R 系列编号，**写入本轮新建的 round 文档（roundN+1）**，不追加进被诊断的旧 round 文档
- 修复方案格式：方案 A/B + 推荐 + 影响范围（file:line）+ 验收标准（含负向断言）
- 涉及外部数据源（akshare/yfinance/DeepSeek）的结论必须标注验证窗口（交易日 9:30-11:30/13:00-15:00），
  窗口外结论标「待交易时段复测」，不得作为「成功/失败」依据

# 测试防护体系缺口分析（强制，阶段 4 内）
对本轮**每个 R 系列发现（bug 类，不含纯数据源环境偶发）**，分析「为什么现有测试防护体系没拦住」，
并把需要补齐的守卫**写成独立设计方案**（与 bug 修复方案并列、可独立实施；只写方案，不写代码）。
参照 `docs/archived/_round4_test-gap-analysis.md`（round4 既有产物，含逐发现映射 + 六类系统性根因）。

## 1. 防护体系现状（每轮实测，不靠文档假设）
盘点本轮防护体系真实状态，逐层标注「能抓到什么 / 抓不到什么」：
- 后端单测（tests/）· verify_e2e.py · data_health_check · patrol.py --full · pre-commit 各档 · 前端 npm test/build
- **门禁自身可信度**（历史教训，防护体系的防护）：
  - verify_e2e 是否真的完整跑完并打印总结（R4-18 教训：脚本自身 UnboundLocalError 仍被当「跑了」→ 门禁输出可信度从未验证）
  - LHCI / 新增门禁**是否真的在本次容器上执行过**（R4-19 教训：门禁存在但从未跑通 = 空转）
  - 与上轮防护体系差异（新增/删除/阈值变化）

## 2. 逐发现映射：为什么防护未识别
对每个 R 发现输出一行映射：
| 发现 | 最应拦截的防护层 | 为何未识别（file:line + 具体断言/阈值） | 应补的守卫（缺口类型） |
每行必须落到**具体断言/阈值/调用点**，禁止笼统「测试没覆盖」。已知缺口类型（round2/3 归纳 + round31 新增）：
- 内容语义断言缺失（e2e 验字段存在不验值合理）
- HTTP 契约层无覆盖（单测直调函数、不测 Query/SSE 形态）
- 前端 mock 数据掩盖真实契约（组件测试形状与后端一致 → 弱断裂测不出）
- 门禁阈值 = 历史问题值（恰压线过关）
- 门禁脚本自身 bug / 门禁存在但未实际执行（空转）
- 多市场/多形态未覆盖（HK/US 个股/资讯端点）
- **两缓存域/多路径数据源不一致**（R94 类：设计喂 hub kline、检查走另一缓存域）
- **正文 vs 结构化数值不同源**（R95 类：文本层引用另一数据源，仅验「200/非空」验不出）

## 3. 系统性根因归并
把逐发现映射归并成 3-8 类系统性根因；每类标注「本轮新出现」或「round2/3 已归纳未收敛」
（已归纳未收敛 = 上轮补的守卫落地失效，需追查为什么失效）。输出一句话总体评价：防护体系
「结构性缺哪一层」而非「这次运气差」。

## 4. 补齐设计（只写方案，不写代码）
对需补齐的守卫输出**独立方案**，格式同修复方案：
- 方案 A/B + 推荐 + 影响范围（file:line，落在测试层 / verify_e2e / patrol / pre-commit / 前端测试）
- 验收含**负向断言**（如「补了内容断言后，再遇同类错误必 FAIL」；「同数据源两路径动量方向一致」）
- 明确守卫应拦截哪一层、为何该层能拦住而现状拦不住
- **负向**：不得为数据源环境偶发加过度断言（会误报——历史 R4-07 教训：真实极端行情被当异常）；
  缺数据时门禁应「诚实降级标注」而非硬 FAIL

## 5. 产物
测试缺口分析表 + 根因归并 + 补齐设计写入本轮新建 round 文档（与 R 系列修复方案并列章节），
作为「防护体系是否真的防住」的对照基线；review 阶段（三轮）须核对补齐设计是否覆盖本轮全部 bug 类发现。

# Review 阶段（三轮结构化）
对**本轮新建的 roundN+1 文档**逐轮执行（被诊断的旧 round 文档不改），每轮输出「发现清单 + 修改清单」：
1. 事实核对：所有 file:line / 数字 / commit 与代码和 git 逐一比对
2. 逻辑一致性：结论与证据互相印证，数字口径统一（吸取 R87 四值口径教训）
3. 完整性：未决项 / 验证窗口 / 风险点是否全覆盖

# 输出格式
每阶段结束汇报：
- 本阶段做了什么 + 结果
- 决策点清单（需拍板的事项，附选项 + 推荐 + 影响范围）
- 风险/待办
结束时按会话记忆惯例用 remember 写入该轮事实（结果一句话 + 关键 commit + 验收口径 + How to apply），
并确认「文档归档」步骤已执行（见 §文档归档：旧轮文档移入 docs/archived/ + 引用同步 + archived/README.md 登记）。

# 禁止事项
- 不写修复代码、不 merge、不 push，除非明确说「开始实施」
- 不用 mock 冒充实现验证；「HTTP 200 / 非空」不算通过，必须内容断言
- 新加外部网络/DB 调用必须有超时/批量/缓存，禁止无超时空转调用
- 不做整体笼统的「分析合理/不合理」评价，必须逐句过四问并附证据
- 陈旧/占位数据下的判断不得当作有效结论采信，必须打标「失效」
