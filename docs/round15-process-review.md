# round15 过程审查（设计与实现流程缺陷与改进）

> **定位**：审查本项目"设计 → 实现 → 验证"流程本身的缺陷（非测试缺陷——测试盲区已在 docs/round15-test-guard-baseline.md 覆盖）。本文档把跨 8+ 轮暴露的**过程性缺陷**归纳为 6 条（D1-D6），给出现有已证明有效的改进，并沉淀为**设计前检查清单**（下轮设计评审直接对照使用）。
>
> **性质**：过程规范 + 检查清单。**不实施**（落地见 §5 优先级）。
>
> **一句话**：测试防护基线解决"怎么验"；本文档解决"怎么设计、怎么实现、怎么让结论可复核"。

---

## 1. 缺陷清单（D1-D6，按阶段）

### 设计阶段

**D1. 方案可行性验证不足——把"未验证的方案"当实施依据**
- **实例**：EM 数据源根因排查走了 A→B→C 三路线：方案 A 容器实测无效后回退（commit c5f8b3d）、方案 B 预检失败（mootdx 协议不匹配，实测 0 行，后证实为**非交易时段误判**——见 D3）、方案 C 机制验证（987317c）后才端到端。大量设计/实施投入浪费在不可行方案上。
- **缺陷本质**：设计评审时没有"最小可行性探针"（spike/probe：容器内 curl、接口探测、最小脚本），方案直接写进实施计划，实施后才发现不可行。
- **防住它**：方案写进文档/计划前，先用 10 行级脚本或单接口探测验证核心假设（数据源可达、协议匹配、字段存在）；**探测克制**（单次探测 + 失败后 ≥60s 间隔，防触发限流——round13 探测曾触发源限流）。探针失败 → 方案不进实施清单。

**D2. 设计结论缺可复核的证据链**
- **实例**：round14 P0-B（策略检查 LLM 超时）根因被推翻重写——初判"30s/35s 外层截断"，review 后经时间线计算 + 代码审计改为"provider 无响应 + 预算-重试不匹配（1 轮双 provider 71.5s 耗光 90s，`(max_retries+1)×2×35=140 > 81`，0.9×预算=81 为一致性断言阈值）"。
- **缺陷本质**：文档结论是"判断"而非"可复核推导"。等 review 用代码行号/时间线打脸后才重写，浪费一轮 review。
- **防住它**：每个结论必须自带证据链——计算式（含数字代入）、`file:line`、实测命令与输出。review 职责从"找矛盾"降为"查证"。

### 实现阶段

**D3. 环境/时机误判导致错误实现**
- **实例**：mootdx 移除后被撤销（commit 7bcab09）——非交易时段测试误判为"协议不匹配"（0 行），回滚后才发现需交易时段复测确认。
- **缺陷本质**：外部数据源（行情/实时）的行为验证没有标注**验证窗口**（交易时段、真实网络环境），实现基于错误前提，造成无效改动 + 回滚。
- **防住它**：凡涉及外部行情源的功能，实现计划必须标注"验证窗口：交易日 HH:MM-HH:MM（如 9:30-11:30/13:00-15:00）+ 真实环境"；非窗口内验证结果打标"待交易时段复测"，不得作为"失败/成功"依据。

**D4. 测试绿 ≠ 功能真（实现验收前置不足）**
- **实例**：round14 诊断 20+ 项问题全逃逸（apply-design 断裂、盈亏色失效、港股自选加载中），反假完成机制（DoD 双证）是**问题爆发后**建立的补救性机制。
- **缺陷本质**：设计评审阶段没有"这个设计会不会产假数据/死代码/伪成功"的检查；实现交付时现实证真依赖自觉而非流程。
- **防住它**：设计评审 checklist 加"非兜底数据""真实调用点""四态 UI"三问（见 §4）；实现完成必须走反假完成清单（已有机制，改为设计阶段前置检查）。

### 验证/治理阶段

**D5. 治理是反应式的——问题爆发后才补门禁**
- **实例**：pre-commit 门禁在 round9 容器复诊断当天补入 4 项门禁类检查（含 verify_e2e 增强）；round15 测试防护基线也是 round14 诊断后补。
- **缺陷本质**：已知问题模式没有**前置沉淀**成"设计前检查清单"，每轮重复踩同类坑（数据源超时、前后端字段错位、CSS 覆盖）。
- **防住它**：把历史踩坑模式（§4 清单）设为**设计评审必查项**，而非等测试逃逸后补门禁。门禁治理约定（新增须说明差异化）保留。

**D6. 性能债被容忍进交付**
- **实例**：性能软门禁是"软"的（不阻断）——watchlist 29.9s、factor-health 10.9s、首页 perf 52 历史都出现过；AGENTS.md 已写"新增 IO 必须带超时/批量/缓存"，但执行靠自觉。
- **缺陷本质**：性能检查没有设计阶段的强制点；复杂度审计（循环内 IO、无超时外部调用）依赖实现者自律。
- **防住它**：设计评审 checklist 加"复杂度审计"两问（新增网络/DB 调用是否有超时/批量/缓存；循环内是否 IO）；性能软门禁性质保留（不阻断），但超阈值必须进"已知性能债"清单（AGENTS.md 已有机制，改为设计阶段预判）。

## 2. 已证明有效的改进（佐证过程改进可行）

这些机制在项目历史中**实际拦截了问题或纠正了流程**，说明 D1-D6 的改进同样值得做：

| 机制 | 何时建立 | 实际效果 |
|---|---|---|

| 反假完成机制（DoD 双证） | round11 教训（P0-3） | 测试绿 + 现实证真缺一不可；脚手架零容忍 |

## 4. 设计前检查清单（下轮设计评审直接对照）

**每份方案文档/设计评审必查（对应缺陷在括号内）：**

1. **可行性探针**：方案核心假设是否已有最小验证（容器内实测/接口探测/最小脚本）？探针命令与结果是否附在文档？【D1】
2. **证据链**：每个结论是否有计算式（数字代入）+ `file:line` + 实测输出？【D2】
3. **验证窗口**：涉及外部行情/实时源的功能，是否标注"交易日 9:30-11:30/13:00-15:00 + 真实环境"？非窗口验证是否打标"待复测"？【D3】
4. **非兜底数据**（同源既有反假完成机制，此处为设计期预判）：该功能输出是否可能只有 fallback/默认值/硬编码？数据源失败时是显式降级标注还是伪装成功？【D4】
5. **真实调用点**：新增函数/端点是否会被真实调用（前端/路由/任务/其它模块）？0 引用 = 脚手架，不进实施。 【D4】
6. **四态 UI**（前端）：loading/空/错误/慢数据四态是否都有 UI？【D4】
7. **复杂度审计**：新增网络/DB/文件调用是否有超时/批量/缓存？循环内是否有 IO？【D6】
8. **已知问题模式**：对照 round14 §4 盲区表 5 类模式（格式断言/mock 理想输入/契约盲区/CSS 零覆盖/降级无门禁），本设计是否触碰其中任何一类？【D5】

**验收时（已有反假完成机制，补一句）**：除测试绿外，逐条回查本清单 4/5/6 项是否成立（4/5/6 为实现期可验证项，1/2/3 为设计期证据、7/8 为设计期审计，均在评审时已过，验收不重复）。

## 5. 落地优先级（建议顺序）

| # | 改进 | 落地形态 | 治 |
|---|---|---|---|
| P1 | 可行性探针前置 | 把 §4-1 写进 AGENTS.md 设计流程（或新方案文档模板） | D1 |
| P2 | 结论证据链 | 方案文档模板加"证据链"必填节；review 只查证不推翻 | D2 |
| P3 | 验证窗口标注 | 涉及行情源的功能计划加"验证窗口"字段 | D3 |
| P4 | 设计前检查清单 | §4 清单落成 `docs/design-checklist.md` 或方案模板 | D4/D5 |
