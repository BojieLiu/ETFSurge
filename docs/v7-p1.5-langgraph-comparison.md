# v7 P1.5 LangGraph 对照选型结论

> 2026-08-31 落地。目的：回答"为什么用/不用 LangGraph？StateGraph 和 Checkpointer
> 分别解决什么问题？"——把 P1 自研循环平移到 LangGraph 后，暴露框架承担什么、
> 业务护栏仍需自写什么。

## 对照结构

| | P1 自研 | P1.5 LangGraph 对照 |
|---|---|---|
| 文件 | `app/agentic/agent_loop.py` | `app/agentic/lg_agent.py` |
| 编排 | 手写 `for` 循环 + 条件 break | `StateGraph` + 条件边（`add_conditional_edges`） |
| 状态 | `RunReport` pydantic | `State` TypedDict + reducer |
| 输出 | `RunReport` | `RunReport`（同构，可对比） |
| 工具执行层 | `Executor` | **复用** `Executor`（共享才公平对照） |
| 测试 | `test_v7_p1_agent_loop.py`（13） | `test_v7_p1_langgraph.py`（8，`-m agentic`） |

## 护栏映射：哪些框架承担，哪些仍需自写

| 护栏 | P1 自研 | LangGraph 对照 | 结论 |
|---|---|---|---|
| 步数预算截断（`max_steps`） | `plan[: max_steps]` + break | **条件边**（`_route` 判断 `executed >= limit`） | **框架承担**：`add_conditional_edges` 天然支持循环终止 |
| 流程编排（plan→execute→循环） | 手写 for | **StateGraph 节点+边** | **框架承担** |
| 步级剩余时间预算（不丢已完成步） | `asyncio.wait_for(remaining)` | 同（`asyncio.wait_for(remaining_s)`） | **自写**：框架不替你做业务超时 |
| 循环检测（同工具同参 2 次） | `Executor._check_loop` | 复用 `Executor` | **复用**：工具执行层，非编排层 |
| 工具白名单 | `Executor` 白名单 | 复用 `Executor` | **复用** |
| 输出 schema 校验（缺 source） | `_validate_output` → ValidationError | `_validate_output` → ValidationError | **自写**：框架不管输出契约 |
| 数据缺失标注（`data=None`） | `data_missing=True` | 同 | **自写** |
| 写操作确认（`write + confirm=False`） | 拒绝执行 | 拒绝执行 | **自写**：业务护栏 |

## 核心结论

**框架解决的是"流程/状态机编排"（StateGraph 节点+条件边+状态 reducer），
但业务护栏一个都省不了**：

1. **StateGraph 承担**：节点编排、条件边循环、状态 reducer（`steps` 用 append
   reducer 累积、`remaining` 用 last-write-wins 覆盖）。让"循环终止"从手写
   `for` + break 变成声明式的条件边。

2. **仍需自写**（框架不替你做业务）：
   - **步级时间预算**：框架的 checkpoint/timeout 是"节点级"或"整图级"，不做
     "每步剩余预算、超时保留已完成步"这种业务语义——仍需 `asyncio.wait_for(remaining)`。
   - **循环检测/白名单/输出校验/数据缺失/写确认**：全是**业务护栏**，与编排框架无关。
     这些 P1 早已写出，LangGraph 对照版要**逐个照搬**才能守住同样边界。

3. **State reducer 是核心概念**：`steps` 需要 `Annotated[list, _reducer_add]`
   （append），因为 LangGraph 状态**默认覆盖**——不显式 reducer 就丢历史步。
   这正是"为什么用框架要理解它的状态模型"的典型例子。

## 选型建议

- **P1 自研已够用**：我们的护栏（步级时间预算保部分结果/循环检测/白名单/输出校验）
  是**业务定制**，LangGraph 不直接提供；自研 `AgentLoop` 200 行内可读可控，
  **不需要引入 LangGraph 增加依赖体积**。
- **LangGraph 的价值**：在"复杂多分支状态机 + 需要人工 checkpointer 持久化/恢复"
  场景才有明显收益。本系统是**线性 plan→execute 循环 + 简单预算终止**，未达到
  需要框架的复杂度拐点。
- **结论**：保留 P1 自研为主实现；LangGraph 对照作为**概念理解 + 面试弹药**
  （回答"框架 vs 手搓"），不替换不进生产链路。
